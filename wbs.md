# WBS（作業見積もり・進捗管理用／社内メモ）

**目的**: 進捗管理と過小見積もり防止のための内部資料。クライアントには提示しない（提案書は `proposal.md` を参照）。
**前提**: 1人で開発を進める想定の見積もり時間。実装スピードは経験・学習状況により変動するため、あくまで目安。
**方針の確定事項**: 記事生成はスプレッドシートのカスタムメニュー「記事を生成」ボタン方式。
課題文の指定に合わせ、**選択した行のキーワードを取得して記事生成する**方式に変更した
（2026-09-16。1行だけ選べば1件、複数行を選べばその分だけ処理する）。
「投稿済み」ステータスへの更新は人が手動で行う（自動検知は実装しない）。
**スコープ調整（実装フェーズで確定）**: 実際のWordPressサイトは使わない。生成した記事本文＋メタディスクリプションを
スプレッドシートに書き出すところまでで完了とする。WordPress連携コードは実装するが、`DRY_RUN=true`のため
実送信はせず、送信予定のペイロードを`Logger.log`で確認する。
**コードの場所**: `gas/`（`appsscript.json` `Config.gs` `Menu.gs` `PromptBuilder.gs` `ChatGptClient.gs`
`WordPressClient.gs` `Main.gs` `README.md`）。セットアップ・実行手順は `gas/README.md` を参照。
ChatGPT APIを使った実際の生成テスト（キーワード5本）は、GASがGoogleアカウントに紐づく実行環境のため、
ユーザー自身のGoogleアカウント上で実行する。

「実績時間」「状態」は作業を進めながら随時更新し、見積もりとのズレを都度確認する。

**見積もりの考え方（講師FB反映・2026-09-16）**: バッファは全タスク一律20%にせず、
タスクごとの「不確実性」（高＝初めて扱う技術要素で調査・手戻りが読みにくい／中／低＝
やり方が分かっている）に応じて、低+10%・中+20%・高+35%を掛けて見積もる。
今回は ChatGPT API・WordPress REST API連携が「高」（初めての技術要素）にあたる。
実績時間を記録するときは、見積とズレた理由も一言添える（例：「3-4：見積1.5h→実績3h／
ChatGPT APIのレート制限エラーの調査に1.5h」）。案件を重ねるごとに「自分がどこを甘く見積もりがちか」
が見えてくるので、次回以降のWBSの精度を上げる材料にする。

**フェーズ1・3の「実績」欄について**: すでに完了したフェーズ1（要件定義・提案）とフェーズ3（実装）は、
Claude Codeが生成・実装した部分。実績列の「約◯分（AI）」は、ストップウォッチでの正確な計測ではなく、
やり取りの回数・複雑さから見積もったAIの処理時間のおおよその目安。人が確認・レビューに使った時間は
含んでいない（ユーザー側で別途指示があれば追記する）。

## 使い方

1. 作業を始めたタスクは「状態」を進行中に、終わったら完了に更新する。
2. 「実績時間」を記録するときは、**見積とズレた理由も一言添える**
   （例：「3-4：見積1.5h→実績3h／ChatGPT APIのレート制限エラーの調査に1.5h」）。
   ズレの理由が積み重なると「自分はAPI連携をいつも少なく見積もりがち」といった傾向が見えてくるので、
   次回以降のWBSはこの記録が見積もりの根拠になる。
3. 新しいタスクを追加するときは、まず「不確実性」（高＝初めて扱う技術要素／中／低＝やり方が分かっている）を決め、
   それに応じたバッファ（低+10%・中+20%・高+35%）を掛ける。全タスクに同じ%を掛けない。
4. フェーズ3（実装）・フェーズ5（テスト）は初めて触る技術要素（ChatGPT APIとWordPress REST APIの連携部分）が
   多く、見積もりが崩れやすいので特に注視する。
