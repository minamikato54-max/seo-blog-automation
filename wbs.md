# WBS（作業見積もり・進捗管理用／社内メモ）

**目的**: 進捗管理と過小見積もり防止のための内部資料。クライアントには提示しない（提案書は `proposal.md` を参照）。
**前提**: 1人で開発を進める想定の見積もり時間。実装スピードは経験・学習状況により変動するため、あくまで目安。
**方針の確定事項**: 記事生成はスプレッドシートのカスタムメニュー「記事を生成」ボタン方式（未生成行を一括処理）。
「投稿済み」ステータスへの更新は人が手動で行う（自動検知は実装しない）。

「実績時間」「状態」は作業を進めながら随時更新し、見積もりとのズレを都度確認する。

## 合計・バッファ

| 項目                                                        | 時間                |
| ----------------------------------------------------------- | ------------------- |
| フェーズ1〜6 合計                                           | 26.5h               |
| バッファ（20%、初見の技術要素の学習コスト・手戻りを見込む） | +5.3h（≒5.5h）      |
| **総見積もり時間**                                          | **約31.8h（≒32h）** |

**予算チェック（目安）**: 提案書の初期費用「4〜6万円ほど」に対して、40,000〜60,000円 ÷ 32h ≈ 時給換算**1,250〜1,875円**となる。美容室LINEbot案件（時給2,400円台）と比べて低めの水準になっている。実際に着手して見積もりが足りないと分かった場合は、次のいずれかで帳尻を合わせる：

1. 提案書の価格帯を見直す（次の案件・追加提案時）
2. 今回のスコープ（`proposal.md`「3. やらないこと」）を厳守し、追加開発をしない
3. 見積もり自体の甘さが原因なら、実績時間を記録して次回の見積もり精度を上げる

## 使い方

1. 作業を始めたタスクは「状態」を進行中に、終わったら完了に更新する。
2. 「実績時間」を都度記録し、見積との差分が大きいタスクがあれば原因（見積もり漏れ／想定外のハマりどころ）をメモしておく。次回以降の見積もり精度向上に使う。
3. フェーズ3（実装）は初めて触る技術要素（ChatGPT APIとWordPress REST APIの連携部分）が多く、見積もりが崩れやすいので特に注視する。
